# Скорость обработки

Норматив кейса: **10 минут записи за 3–5 минут** на процессоре ноутбука. Конвейер рассчитан на этот запас, а не на мгновенный ответ.

## Что занимает время

Почти всё время — это Whisper. Проверка файла, расшифровка Fernet и перевод в WAV 16 кГц mono занимают секунды даже на 15-минутной записи. Оценка качества по готовому тексту — доли секунды.

## Как ускоряется длинный звонок

| Приём | Зачем |
|---|---|
| Модель `base`, `float32`, CPU | баланс точности и скорости для русского языка; int8 на части CPU портит текст, см. замеры ниже |
| VAD | тишина и длинные паузы не считаются |
| `condition_on_previous_text=false` | длинный файл не зацикливается на повторе фразы |
| Пакетная расшифровка от 90 секунд | `BatchedInferencePipeline`, размер пакета `WHISPER_BATCH_SIZE` (по умолчанию 8) |
| Запись от 3 минут, включая норматив 10 минут | луч декодера 1 и границы сегментов вместо пословной разметки. Так 10 минут укладываются в 3–5 минут на CPU ноутбука. Роли реплик остаются |
| Без текстовой подсказки на длинном файле | подсказка не копируется в каждое окно и не портит текст |
| Пословные таймкоды только до 3 минут | на коротких записях реплики собираются по словам (точнее границы ролей). От 3 минут пословная разметка выключена, реплики строятся по границам сегментов Whisper. В стерео-записи роли всё равно берутся из каналов |
| Прогресс в базу не чаще раза в 1,2 с | очередь не тормозит сама себя |
| Прогрев модели при старте | первый звонок не ждёт загрузку весов, если модель уже на диске |

Короткие записи (до 90 секунд) идут обычным проходом с короткой банковской подсказкой: на них пакет не даёт выигрыша, а подсказка помогает терминам.

Луч декодера `WHISPER_BEAM_SIZE=5` оставлен ради качества. `best_of` при температуре 0 не используется: он не улучшает текст и тратит время.

## Если 10 минут не укладываются в 5

1. Поставьте `WHISPER_CPU_THREADS` равным числу ядер, если автовыбор взял мало.
2. Уменьшите `WHISPER_BATCH_SIZE` до 4, если ноутбук упирается в память и начинает свопить. Своп медленнее любого пакета.
3. Для демонстрации скорости, не для боевой оценки: `WHISPER_MODEL=tiny` или `WHISPER_BEAM_SIZE=1`.
4. Для точности в ущерб времени: `WHISPER_MODEL=small`.

Очередь по умолчанию берёт один файл (`MAX_PARALLEL_JOBS=1`). Два файла на одном CPU почти всегда медленнее, чем по очереди: модель и так занимает все ядра.

## Что видит человек в кабинете

Пока статус «обрабатывается», досье и журнал обновляются сами и показывают процент. Для готового звонка рядом с длительностью написано, уложилась ли обработка в половину длины записи (5 минут на 10 минут аудио).

## Выбор модели

`WHISPER_MODEL` (`tiny`, `base`, `small`, `medium`, `large-v3`) теперь действительно выбирает модель: она ищется в `data/models/faster-whisper-<имя>/`, при первом запуске скачивается туда один раз, дальше работа офлайн. В `WHISPER_MODEL` можно указать и путь к своей папке модели. Раньше путь был жёстко `faster-whisper-base`, и `small` молча игнорировался, если base уже лежала на диске.

## Как замерить у себя

```bash
python scripts/benchmark.py make-sample --minutes 10 --out data/bench/sample_10min.wav   # из MInDS-14, эталон в .txt
python scripts/benchmark.py speed --audio data/bench/sample_10min.wav --models base,small --runs 3
python scripts/benchmark.py speed --audio ваш_звонок.mp3 --models base --compute-type float32
python scripts/benchmark.py wer --models base,small --clips 40
```

`speed` меряет весь конвейер, как в очереди: перевод в WAV, Whisper, разметку ролей и оценку. RTF = время обработки / длительность записи; норматив кейса (10 минут за 3-5 минут) - это RTF 0,3-0,5. Если рядом с файлом лежит `.txt` с эталоном, считается и WER/CER. Результаты дописываются в `data/bench/results.jsonl`.

## Замеры 17.11.2026

Машина: облачная VM, Intel Xeon (Sapphire Rapids, AVX-512 и AMX), 8 vCPU, 15 ГБ RAM, Linux, Python 3.13.5, faster-whisper 1.1.1, ctranslate2 4.9.0. Это не ноутбук: на ноутбуке время будет больше, его нужно замерить отдельно.

Запись: 10,23 минуты (613,8 с), склеены 69 клипов MInDS-14 ru-RU (телефонные запросы клиентов банка, 8 кГц) с паузой 0,6 с. Это один голос на клип, а не настоящий диалог оператора и клиента. Режим длинной записи: пакетный проход, луч 1, без пословных таймкодов.

Скорость, весь конвейер (по 3 прогона, разброс в пределах 1-2 с):

- `base`, float32, 8 потоков: 13,0-13,8 с, RTF 0,021-0,022, WER 0,295, CER 0,147.
- `small`, float32, 8 потоков: 33,6-34,6 с, RTF 0,055-0,056, WER 0,217, CER 0,119.
- `base`, float32, 4 потока: 12,2 с, RTF 0,020 (1 прогон).
- `small`, float32, 4 потока: 35,8 с, RTF 0,058 (1 прогон).
- `base`, int8: 7,6-9,9 с, RTF 0,012-0,016, но текст неверный: WER 0,82-0,98.
- `small`, int8: 25,1-26,6 с, RTF 0,041-0,043, текст неверный: WER 0,90-0,99.
- `base`, int8_float32: 9,1-10,9 с, RTF 0,015-0,018, текст неверный: WER 0,88-0,96.
- `small`, int8_float32: 18,8-24,6 с, RTF 0,031-0,040, текст неверный: WER 0,67-0,98.

Прогоны int8_float32 частично шли одновременно с установкой пакетов на той же машине, поэтому их время может быть немного завышено; на WER это не влияет.

WER/CER на 40 отдельных клипах MInDS-14 (короткие записи, обычный проход с лучом 5):

- `base` float32: WER 0,239, CER 0,152, 39,4 с на 40 клипов.
- `small` float32: WER 0,168, CER 0,092, 76,3 с.
- `base` int8: WER 0,675, CER 0,581.
- `small` int8: WER 0,293, CER 0,206.
- `base` int8_float32: WER 0,398, CER 0,304, 29,0 с.
- `small` int8_float32: WER 0,290, CER 0,172, 48,7 с.

Выводы:

- На этой машине норматив выполняется с большим запасом: 10 минут обрабатываются за 13 с (`base`) и 35 с (`small`) в float32. Для ноутбука цифр нет, их нужно снять скриптом выше.
- `small` точнее `base` (WER 0,22 против 0,30 на длинной записи, 0,17 против 0,24 на клипах) и в 2,5 раза медленнее.
- **int8 на этой VM выдаёт мусор**, и результат меняется от прогона к прогону: тот же 30-секундный отрывок в int8 распознавался то правильно, то пустой строкой или набором английских слов. На коротком отрывке int8_float32 сначала выглядел стабильным, но на полной 10-минутной записи он ломается так же, как int8 (WER 0,67-0,98). Стабилен только float32. Похоже на проблему int8-ядер ctranslate2 4.9.0 на этом процессоре (AVX-512/AMX). На других CPU int8 может работать нормально, но проверять это нужно скриптом `speed` с эталоном, а не на глаз. Поэтому с 17.11.2026 по умолчанию `WHISPER_COMPUTE_TYPE=float32`: он в 1,3-1,7 раза медленнее int8, но норматив всё равно выполняется с большим запасом (RTF 0,02-0,06 при нормативе 0,3-0,5). Включать `int8` или `int8_float32` стоит только после проверки WER скриптом `speed` на целевом CPU.

## Локальная LLM (замер 17.11.2026)

Та же VM, Ollama 0.40.16 на CPU, 14 демо-звонков по 5-9 реплик, `python scripts/benchmark.py llm --model ... --calls 14 --warmup`:

- `qwen2.5:7b-instruct`: валидный JSON 14/14, 11,1-20,2 с на звонок, в среднем 14,7 с, загрузка модели 19 с.
- `qwen2.5:3b`: валидный JSON 14/14, 5,1-10,4 с, в среднем 7,4 с, загрузка 9-10 с.

С LLM весь звонок 16-38 с обрабатывается за 16-29 с, почти всё время - модель. Модель получает не больше 12 000 символов текста (начало и конец), запрос один на звонок. 10-минутная запись в docker compose с `qwen2.5:7b-instruct`: весь звонок 91,8 с, из них LLM 80 с (Whisper и правила около 12 с). Первый запрос после старта Ollama дольше на загрузку модели (28 с на клипе 10 с).

AMD Ryzen AI 9 HX 365 (20 потоков), 24 ГБ RAM, Windows + Docker Desktop (WSL2), 8 потоков Whisper. Запись `samples/bench_synth_10min.mp3` (10,7 мин, 10 синтетических звонков), `small`, float32: весь конвейер 57,4 с, RTF 0,09. Норматив (5 минут на 10 минут записи) выполняется с запасом примерно в 5 раз. С LLM `qwen2.5:7b-instruct` сверху добавляется время модели (на VM около 80 с на длинный звонок).
